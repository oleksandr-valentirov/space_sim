# engine-render

Етап F (Milestone 2), ROADMAP.md. Закрито: **F1** (вікно, очищення),
**F2** (трикутник), **F3** (reversed-Z), **F4** (camera-relative). У
роботі: **F5** (сфера в реальному масштабі). Кожен крок F1–F4 має власний
вимір, не лише «працює» — вони нижче, бо саме тут найлегше витратити
контекст на переоткриття вже знайденого.

Джерело істини — [PROJECT.md](../../PROJECT.md) §7 (рендер) і
[ROADMAP.md](../../ROADMAP.md), етап F.

## Структура: два шляхи до одного кадру

`engine/src/frame.rs` малює, **не знаючи про вікно** — лише формат
цілі й `wgpu::TextureView`. Далі той самий `Frame`:

- `app.rs` — у вікно, через `winit` + `wgpu::Surface`. Те, що бачить гравець.
- `shot.rs` — у текстуру й PNG, без вікна. **Це і є спосіб перевірити
  рендер**: «вікно відкрилось і не впало» нічого не доводить — чорний
  кадр і правильний виглядають однаково при простому запуску.

```
gpu.rs          Gpu { instance, adapter, device, queue } — один на процес
frame.rs        Frame — пайплайн + draw(), незалежний від цілі
app.rs          вікно (winit), surface, цикл подій, resize
shot.rs         кадр → текстура → буфер → PNG, read_back() — спільний з depth_probe
depth.rs        reversed-Z: формат, COMPARE, CLEAR, матриці, resolvable_gap()
depth_probe.rs  вимірювач роздільності глибини (два квади, частка кадру де ближчий виграв)
camera_probe.rs camera-relative vs наївний шлях — зсув центру ваги об'єкта в пікселях
main.rs         CLI: --shot, --frames, --vsync/--no-vsync, --depth-probe, --width/--height
```

`tools/gpu-probe` і `tools/slang-probe` — окремі бінарники, розвідки
(ROADMAP P0/P1), у гру не йдуть.

## F3 — reversed-Z: що виміряно і чому це важливо саме зараз

`z_ndc = near / z` (нескінченна далека площина). Роздільність — **стала
частка відстані**, `near` на неї не впливає:

```
Δz_min ≈ z · 2⁻²⁴ ≈ z · 6·10⁻⁸        (engine/src/depth.rs::resolvable_gap — оцінка згори, ×1.4 консервативна)
```

Виміряно (`cargo run -p engine -- --depth-probe`), частка кадру де
ближчий виграв:

| відстань | зазор | reversed-Z | звичайна |
|---|---|---|---|
| 10⁵ м | 1 м | 1.000 | **0.000** |
| 10⁶ м | 1 м | 1.000 | 0.000 |
| 10⁷ м | 1 м | 1.000 | залежить від заліза, див. нижче |
| 10⁸ м | 1 м | 0.000 (межа float32, не баг) | 0.000 |

**Один depth buffer тримає приблизно сім порядків відстані** — це і є
кількісна причина, чому PROJECT.md §7 вимагає багатопрохідного рендера
по діапазонах (чотири проходи: зорі, scaled space, поверхня, локальна
сцена). Не запас, а необхідність.

### ⚠ Апаратно-залежна межа — виявлено на Steam Deck (RADV VANGOGH)

Клітинка **10⁷ м / зазор 1 м** лежить рівно на межі округлення float32:
справжня (double) різниця `z_ndc` двох поверхонь — частка однієї ULP.
На CPU-растеризаторі (`llvmpipe`) звичайна проєкція там програє (0.000,
як задокументовано в таблиці), але на апаратному Vulkan того самого GPU
(`AMD RADV VANGOGH`) — **вигравала** (1.000). Причина не в коді рушія:
на цій межі результат вирішує деталь конкретного растеризатора (FMA у
GPU-компіляторі шейдера, апаратний `rcp` замість честивого ділення), а
не гарантія IEEE-754. Перевірено трьома бекендами на одній машині —
подробиці й таблиця в ROADMAP.md, розділ F3.

**Висновок для будь-якого майбутнього виміру глибини:** не роби
твердження «X проти Y на відстані Z» на клітинці, де `resolvable_gap(Z)`
близька до самого зазору — там відповідь залежить від GPU, а не від
геометрії. Бери зазор із запасом (як тест зараз робить: той самий 10⁷ м,
але 100 м зазору — 0.000 однаково на `llvmpipe`, `RADV` і `radeonsi`/GL).

## F4 — camera-relative: що виміряно

PROJECT.md §7 рішення 1: світові координати ніколи не в `float`.
`(світ_об'єкта − світ_камери) as f32`, не `as f32 − as f32`.

**Стовпець camera-relative однаковий (3.15/3.54 px) на всіх восьми
порядках відстані до початку координат, від 10³ до 10¹¹ м.** Наївний
шлях не тремтить — він **зникає**: на 10⁸ м уже помітно гірший, на 10⁹ м
об'єкт випадає з кадру. Поріг — 10⁸ м, на порядок ближче за 1 а.о. з
початкового критерію: camera-relative потрібен вже для навколоземних
відстаней, не лише міжпланетних.

## Шейдери

**Slang → WGSL**, не SPIR-V (`naga` не приймає capability
`DrawParameters`, яку Slang оголошує заради `SV_VertexID`). WGSL-файли в
`engine/shaders/*.wgsl` — згенеровані, комітяться, `include_str!`
вбудовує їх у бінарник (шейдер — частина програми, не ассет, який можна
підмінити на диску).

## Запуск і перевірка

```sh
cargo run -p engine                          # вікно
cargo run -p engine -- --frames 60           # вікно, 60 кадрів і вихід (без vsync — інакше залипає, коли компонувальник не показує вікно)
cargo run -p engine -- --shot build/f.png    # знімок без вікна — основний спосіб перевірки в CI
cargo run -p engine -- --depth-probe         # таблиця роздільності глибини, reversed-Z проти звичайної
cargo run -p engine --example f4             # camera-relative розвідка (F4)
cargo test -p engine                         # tests/camera.rs, tests/depth.rs, tests/shot.rs
cargo run -q -p gpu-probe                    # адаптери й bindless-фічі на цій машині
```

## Коли оновлювати цей скіл

- Закрито F5 або F6 — додай розділ із тим, що саме виміряно (як у F3/F4
  вище), онови «у роботі: …» на початку.
- З'явився новий модуль у `engine/src/` — онови таблицю структури.
- Зміна в `depth.rs` (формат, порівняння, формула) — звір розділ F3 з
  кодом напряму, це числа, які легко застаріти непомітно.
- Якщо хтось виміряє цю саму апаратну межу на іншому GPU (NVIDIA, Intel,
  інший AMD) — додай рядок у таблицю бекендів в ROADMAP.md і онову
  висновок тут, якщо він зміниться.
